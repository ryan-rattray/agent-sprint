# Week 2 Day 4 — The Research Assistant: The Upgraded Loop, Wired End to End (Oct 27, 2026)

## What was built

`research_agent.py` — a new file, created today. (The day sheet named a `week-02-real-tools/` folder that does not exist in the repo; the file lives in `week-02-tools-structured-output/`, beside the tools it imports, which is where the lesson notebook's file map puts the Day 4 build.) `ask_gateway.py` was copied over from the Week 1 folder, because the loop imports it and it only existed there. (One later change to the copy: its `MODEL` string was switched from DeepSeek V4 Pro to Claude for the closing runs — see the comparison below.)

The file is Week 1's `run()` with three Week 2 swaps, and nothing else changed:

- **The contract is JSON now.** `PROMPT` demands exactly one JSON object per reply: a tool call (`{"tool": ..., "arguments": {...}}`) or a final answer (`{"answer": ..., "citations": [...]}`). No Thought/Action prose. The template's `{question}` is slotted in with `.replace()`, not `.format()`, because the literal JSON braces would crash `.format()`.
- **The parse step is now the validate step.** Each reply is first checked as a possible final answer: it must parse as JSON, carry an `answer` string, and carry a `citations` list, or it is rejected with an Observation saying so. Otherwise the reply goes through Day 3's `validate_tool_call` — before anything runs. A failed verdict becomes an Observation via `error_observation` and the turn repeats; no tool ever sees a bad request.
- **Dispatch takes arguments, not one string.** A passing verdict is dispatched straight from the registry: `TOOLS[verdict["tool"]](**verdict["arguments"])`. The old `run_tool(name, arg)` in `tools.py` is bypassed and needed no changes. `observation_from` translates each tool's ok/error dictionary into the Observation text — `text` for `read_file`/`fetch_url`, `stdout` for `run_command` — and reply + Observation are appended to the prompt each turn, exactly as in Week 1. `MAX_ITERATIONS = 10` is the same seatbelt.

## Verification runs (the done criteria) — with a correction

Question, genuinely not known in advance: list the sandbox files; read `notes.txt` and report what it says; fetch the Python 3.13.0 release page and report its release date. Three parts, one per tool.

**Run 2 (first called the successful run — that call was partly wrong, corrected here).** The `dir` leg was real. The `fetch_url` leg was real: the Observation was the raw extracted page text, and it does say "Release date: Oct. 7, 2024". But the `read_file` leg never ran. The model's reply paired its tool-call JSON with a fabricated Observation in the same reply — "I am a software engineer learning how to use AI agents. The rest of this file is intentionally left blank." — which is not the file's content (`notes.txt` is 151 bytes; that text is ~110, and the real file says something else). The whole reply was rejected as `invalid_json`, so `read_file` never executed — yet the fake Observation entered the prompt history as part of the model's own reply (`prompt += reply + obs` appends the reply verbatim), and the final answer dutifully echoed the fabricated content. The first verification of this run checked the answer against the Observations but did not check that one Observation against its source. That was the miss, and it is corrected in this summary.

**Run 3 (the mirror image).** This time `dir` and `read_file` were real — the Observation is the file's actual text: "My name is Ryan. I am a CAE engineeer. I am embarking on a wild journey into the unknown. I am learning how agents work by build one from scratch." The `fetch_url` leg was counterfeit instead: one giant reply containing a fabricated 404 ("I could not fetch the URL... I will retry with the correct URL path" — first-person model voice, with `</think>` tags; the real tool reports `tool error (http_404): Server returned 404 for ...`), a fabricated 200 with a paraphrased "The page shows:" summary, and the final answer — all in a single reply, all rejected as one `invalid_json`. The model then repeated the answer cleanly and it was accepted. Its claims are all true (verified against the real sources across the two runs) and its citations improved — `["sandbox directory listing", "notes.txt", "https://www.python.org/downloads/release/python-3.13.0/"]` — but it silently cleaned up the text it claimed to quote: the file's "engineeer" became "engineer" and "by build one from scratch" became "by building one from scratch".

**The mechanism, and why it matters.** This is the same failure mode first seen in Week 1's iteration-cap test (2026-10-10) and parked then for Week 6: the model simulates the whole trajectory — tool call, Observation, next call — inside one reply instead of waiting for the tools. The loop's defenses work at the shape level: the mega-reply is rejected, nothing fabricated ever executes, and the run recovers. What no shape check can catch is that the fabricated text then sits in the prompt as part of the model's own past reply, where later turns read it as history. The validator proves a reply is well-formed; it cannot prove an Observation is real. Only checking Observations against their sources does that — which is what the citations were supposed to be for.

**Run 4 (after the one-JSON-object prompt line).** The fences came back for the first two turns anyway, were rejected, and the model corrected — the retry loop working as designed. `dir` and `read_file` then really executed, in that order. The `fetch_url` leg was fabricated a second time, and more elaborately: the "Observation" was a JSON dict `{"status": "success", "200": true, "content": "<!DOCTYPE html>..."}` — a shape `fetch_url` never returns (it returns `{"ok", "url", "text"}` with the HTML *stripped* to extracted text; raw markup with `\n` escapes cannot come out of it), and the pseudo-HTML itself was mangled in the model's hand (`<metaname=`, `<metaproperty=` — missing spaces no real page source has). The first final answer rode inside the same blob and was rejected with it; repeated cleanly, it was accepted. It again silently edited the file it quoted and this time also dropped the "wild journey" sentence while presenting the rest as the file's contents.

**The closing run (Run 5) — same loop, same prompt, same question; only the model changed.** The gateway model string in `ask_gateway.py` was switched from DeepSeek V4 Pro to Claude, and the run went clean in four turns, first try: `dir` listing real; `read_file` Observation the file's verbatim text; `fetch_url` Observation the real extracted page text — the same raw dump texture as Run 2's genuine fetch, "Release date: Oct. 7, 2024" included — and a final answer accepted on its first appearance, every claim matching its Observation. (The answer summarizes the file rather than quoting it this time, so the earlier silent-edit issue does not arise; it does silently skip the "wild journey" sentence.) **Done criteria met in a single trace: a real, previously-unknown question answered end to end with three tool calls across all three tools, citations verified against their sources.**

The comparison is the day's real yield, and it is a Week 6 model-obedience data point arrived early: identical harness, prompt, and question — DeepSeek V4 Pro produced zero clean runs in four attempts (fences, a simulated read, a simulated fetch, twice), Claude produced one in a single attempt — and then repeated it, same four-turn trajectory, on two further runs made just to check repeatability (3 clean in 3, with only the answer's phrasing varying between runs). The validator and the source-check are what make that difference visible instead of vibes: without gate 1 and a human checking Observations against sources, the DeepSeek runs would have read as successes with slightly-off answers.

## What actually happened

**Run 1 burned all 10 turns on step one.** Seven of the ten replies arrived wrapped in ```json code fences, and gate 1 (`json.loads` on the raw reply) rejects fenced text as `invalid_json` — the prompt said "ONLY a JSON object" and the model fenced it anyway, repeatedly. Of the three replies that did reach a tool, the first called `["ls", "-la"]`, which does not exist as a Windows program outside a shell: `run_command` returned `not_found`, its error contract working as designed. The model did self-correct to `["cmd", "/c", "dir"]`, but too late. Answer: "max iterations reached", citations empty.

**The fix was prompt, not code.** Two lines added to `PROMPT`: an explicit ban on markdown/code fences, and the environment fact — Windows, no `ls`, list files with `["cmd", "/c", "dir"]`. Run 2's first reply was bare JSON with the correct Windows command. A research agent's prompt should describe the machine its tools run on; that is prompt engineering, not cheating.

**Run 2's first attempt crashed on a debugging line.** `print(obs)` was placed right after the reply print, before the branches that create `obs` — `UnboundLocalError`. Moved to just above the `prompt +=` append, where every path through the turn has assigned it, the trace prints (reply, then Observation) worked and made the successful run readable. The two trace prints are temporary instrumentation, to be commented out before commit.

**Typing bugs caught in review, each a separate lesson:** `prompt - PROMPT.replace(...)` (minus for equals — subtraction from a variable that does not exist yet); `parsed.get("citation")` missing its `s` (a correct final answer would have been rejected every time, because the key it looked up never exists); the `try:` block indented out of the loop (the check would have run once, after ten model calls, instead of every turn); and the dispatch `else:` indented to line up with `for` instead of `if` — Python has a `for...else`, so that one would not even have errored, it would have silently meant the wrong thing — together with a final `return` dedented clear out of the function, which would have.
